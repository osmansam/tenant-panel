# Generated Relation Columns Design

## Goal

Allow a table configured in tenantPanel to fetch records from a selected reference schema and generate one Boolean membership column per referenced record. Each generated cell represents whether the referenced record's ID exists in an explicitly selected array field on the table row.

## Configuration

`TableComponentConfig` gains an optional `generatedRelationColumns` array so a table can define one or more independent generated column groups.

```json
{
  "id": "locations",
  "arrayField": "locations",
  "sourceSchemaName": "location",
  "sourceIdField": "_id",
  "sourceLabelField": "name",
  "sourceLimit": 100,
  "booleanEditToggle": {
    "toggleId": "locationEdit",
    "when": true
  }
}
```

- `id` is a stable group identity generated by tenantPanel and retained when the group is renamed or reordered. Runtime column keys use `${group.id}:${normalizedSourceId}`.
- `arrayField` is the destination array on each table row. tenantPanel labels this **Row array field** and offers compatible array fields from the table row schema.
- `sourceSchemaName` is the schema whose records become generated columns.
- `sourceIdField` supplies the membership value added to or removed from `arrayField`; it defaults to `_id`.
- `sourceLabelField` supplies each generated column heading.
- `sourceLimit` bounds generated columns for the group. It defaults to `100`, must be between `1` and `100`, and is enforced when source records are converted into columns.
- `booleanEditToggle` uses an existing table-local toggle. Matching state renders editable switches; the opposite state renders readonly check/cross icons. With no binding, generated columns use editable switches. The name and semantics match static Boolean columns.

## Runtime Data Flow

Both paginated and unpaginated runtimes fetch source records for each configured schema through the existing dynamic-item query layer, bounded by the largest configured `sourceLimit` needed for that schema. One runtime column is generated for every accepted source record up to each group's limit.

Column generation is a shared pure operation. Data fetching remains in the runtime components, which pass configuration, source records, toggle state, and a membership callback into `buildGeneratedRelationColumns`. This keeps paginated and unpaginated behavior identical.

All identity operations use one helper:

```ts
normalizeRelationValue(value: unknown): string | null
```

It returns `null` for `null`, `undefined`, empty strings, and unsupported empty values; trims strings; stringifies finite numbers and bigint values; unwraps serialized `{ "$oid": string }` values; and otherwise uses a stable primitive string representation when possible. The helper is used for membership detection, duplicate prevention, removal, generated column identity, and label fallback.

For a table row and source record:

1. Read `row[arrayField]`, treating a missing or non-array value as an empty array.
2. Compare its members with `source[sourceIdField]` using `normalizeRelationValue` so strings, numbers, and serialized ObjectIDs match consistently.
3. In readonly presentation, render `IoCheckmark` when present or `IoCloseOutline` when absent.
4. In switch presentation, toggling on appends the source ID only if it is not already present. Toggling off removes matching IDs.
5. Update the local row membership snapshot immediately, then send an update containing only `{ [arrayField]: nextArray }` through the existing `updateDynamicItem` mutation. Subsequent rapid switches calculate from that latest local snapshot rather than stale server data.

The original source ID value is preserved when appending; normalization is used only for comparison.

Source records are deduplicated by normalized source ID before applying the group limit; the first occurrence wins. A missing or whitespace-only label falls back to the normalized source ID.

## Tenant Designer

Add a **Generated Relation Columns** section to table settings. Each group supports add, reorder, and delete controls plus dropdowns for:

- Row array field
- Source schema
- Source ID field
- Source label field
- Source record limit, defaulting to 100 and capped at 100
- Boolean edit toggle
- Show switch when On/Off

Changing the table row schema refreshes the row-field options and clears `arrayField` if it disappears or is no longer array-compatible. Changing the source schema refreshes source ID and label options and clears selections that do not exist in the new source schema. Row array choices are restricted to compatible array fields; if item-type metadata is unavailable, all array fields are offered.

## Validation and Failure Handling

Backend validation requires:

- non-empty and table-unique stable `id`;
- non-empty `arrayField`, `sourceSchemaName`, and `sourceLabelField`;
- a non-empty `sourceIdField` when supplied;
- `sourceLimit` between 1 and 100 when supplied;
- any `booleanEditToggle.toggleId` to reference a toggle defined in the same table.

Runtime behavior fails safely:

- unavailable source data generates no columns;
- records missing the configured ID are skipped;
- missing labels fall back to the normalized ID;
- a missing toggle reference fails open to switch presentation;
- mutation errors use the existing dynamic-update error handling.

Groups may target the same `arrayField`, but those groups must use compatible, non-overlapping ID namespaces because the destination stores raw IDs without source-schema metadata. tenantPanel displays a warning when multiple source schemas target the same row array field.

## Compatibility

The feature is generic and contains no location-specific code. Existing static columns, visibility bindings, Boolean editability bindings, request effects, and generated table behavior remain unchanged. Saved tables without `generatedRelationColumns` behave exactly as before.

## Testing

- Backend BSON/JSON round-trip and validation tests.
- Pure frontend tests for canonical normalization, column expansion, first-ID deduplication, record limits, normalized membership, add/remove behavior, empty labels, missing data, and edit-toggle evaluation.
- tenantPanel cleaner tests for preserving valid groups and false toggle states.
- Paginated and unpaginated runtime integration through the shared pure helpers.
- Verification that rapid membership updates use the latest local array snapshot.
- Full backend/frontend test suites and both frontend production builds.
