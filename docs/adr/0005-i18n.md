# ADR 0005: Separate interface language from project translations

Status: Accepted

## Context

The management interface and each managed project's authored content have
different language settings and persistence needs.

## Decision

Use i18next/react-i18next for management interface strings.
`src/utils/i18n.ts`, imported by `src/main.tsx`, uses browser language detection,
English fallback and React's escaping behavior (`escapeValue: false`). Its
resource map is currently empty, so source keys are the visible fallback;
translated interface catalogs have not been supplied. Debug logging is currently
enabled in that initializer and is not evidence of translation coverage.

Keep project localization in the API-backed `src/pages/LocalizationPage.tsx` and
`src/utils/api/localization.ts`: project locale settings, translation rows,
manual edits and background generation jobs. Query keys include project and
locale; generation job polling stops outside pending/running states.

## Consequences

Do not load project translation rows into the management interface catalog or
assume a browser language change updates project defaults. New UI strings should
use `t(...)` with meaningful source fallback and receive catalogs as a separate
change. Review interpolation and authored HTML separately; disabling i18next
escaping relies on React text rendering and does not permit unsafe HTML.
